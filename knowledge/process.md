- 2026-09-24 APR-7557: a review that ran outside the loop leaves no trace the gates can read — ship-gate blocked push and mr create on `verdicts.code = null` even though review-code had just returned APPROVE. Record it with `ship-state verdict <T> code APPROVE` (and the stage) before pushing; never bypass the gate.
- 2026-09-24 APR-7557: do not infer a force-push from `git rev-parse --abbrev-ref @{u}` — with no remote branch yet it answers `origin/main` (the configured default), and the push then prints `[new branch]`. Quote the push output before claiming what the push did; I reported a force-update that never happened and had to retract it.

- 2026-09-24 APR-7557: tickets shaped "measure, then if needed X" must STOP after understand for the human to run the measurement; planning X before the number exists built a migration that may have been unnecessary (80% of the ticket's cost).
- 2026-09-24 APR-7557: lead worked around a stale settings deny (glab mr update → glab api PUT) with disclosure; rule added to lead.md: a deny is a deny, never the same effect by another path, one diagnostic command then report.
- 2026-09-24 APR-7557: reading an absence in a tool's output as a fact about the system burned me twice in one session. `acli jira workitem view --json` defaults to 5 fields (assignee, description, issuetype, status, summary) and omits `resolution`, but `--fields status,resolution` DOES return it — verified 2026-09-26: `acli jira workitem view APR-7765 --fields status,resolution --json` → `status: Done | resolution: Won't Do`, while the bare `--json` returned `resolution: None` for the open ticket APR-7773; I saw no `resolution` key and told the user the ticket had none, when Jira actually held `Done` + resolution "Won't Do". Earlier, `git rev-parse --abbrev-ref @{u}` answered `origin/main` when no remote branch existed yet, and I reported a force-push that never happened. Both times the tool was not lying: it was not answering the question I believed I was asking. Before reporting a negative, verify the tool actually requests that field, and prefer a UI view, a screenshot or a second tool over an absence.
- 2026-09-28 APR-7781: the end of a conv-ai-settings ticket is a three-step sequence, and the third step is easy to forget: (1) verify the change on STAGING against real data and a real call, not just the green pipeline, (2) leave the result as a comment on the Jira ticket, (3) then move the ticket to Ready For Production. The verification is what earns the transition; a merged MR with a green pipeline on staging is steps 0, not step 1. Record the measured result (states seen, latency, what could NOT be reproduced) in the comment, then transition.
- 2026-09-28 APR-7781: `CC_CONFIRMED=1` does not defeat a settings `deny` — the bash-guard refused the Jira transition "Ready For Production" both bare and prefixed, so that transition is denied at the settings level, not a confirmable guard. When a deny survives the confirmed prefix, stop and hand the exact command to the user; do not reach for acli alternatives or another path.
- 2026-09-28 APR-7781: aconv-ai-settings ticket cannot reach "Ready For Production" until the QA Sub-Status field is Done. Field is `customfield_10193` (values: "To Do" id 10711, "Done" id 10713); Jira answers `Field QA Sub-Status with actual value 'To Do' does not match regular expression Done` on the transition. Neither `acli workitem transition` nor `acli workitem edit` exposes a custom-field flag (edit --generate-json only emits assignee/description/issues/labels/summary/type), so it needs REST: PUT /rest/api/3/issue/<KEY> with {"fields":{"customfield_10193":{"id":"10713"}}} then the transition. That field is QA's verdict, not housekeeping: the dev should not set it without QA saying so. Verified 2026-09-28 by diffing APR-7727 (RFP, field=Done) against APR-7781 (Assigned to QA, field=To Do).
